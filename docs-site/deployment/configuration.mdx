## The contract

The server is configured like any ASP.NET Core app. Environment variables carry only connections to resources and identity. Everything else is behavior, with a default in `src\VideoSafetyStudio.Server\appsettings.json`, and you override it when you need to.

Later sources win:

1. `appsettings.json`, then `appsettings.<Environment>.json`.
2. Environment variables, where `:` becomes `__`. App Service app settings are environment variables, so `AzureMl:Armed` is the app setting `AzureMl__Armed`.
3. Azure Key Vault, only when `KeyVault__Uri` is set. A secret name uses `--` for `:`, so the secret `AzureMl--MaxUploadMb` overrides `AzureMl:MaxUploadMb`.

There are no `WAN_STUDIO_*` settings on the server. The older JSON-in-an-environment-variable settings (`WAN_STUDIO_FOUNDATION_JSON` and friends) are ignored by current images, so delete them from a site that was built earlier. `WAN_STUDIO_PYPI_INDEX` and `WAN_STUDIO_CACHE` still exist, but they belong to the operator scripts and the server never reads them.

The repository's `docs\configuration.md` has the full key list, including the local development and ComfyUI keys that a hosted deployment does not set. This page was checked against `infra\portal.tf`, `scripts\Invoke-WanSafetyStudio.ps1` and `appsettings.json`.

## Who owns which setting

Three actors write app settings, and Terraform deliberately ignores the ones the scripts own. The `ignore_changes` list in `infra\portal.tf` shows which:

```hcl title="infra/portal.tf"
lifecycle {
  ignore_changes = [
    app_settings["AzureMl__Armed"],
    app_settings["AzureMl__Release__EnvironmentId"],
    app_settings["AzureMl__Release__ModelsRef"],
    app_settings["AzureMl__Release__CodeUri"],
    app_settings["Auth__ClientId"],
    app_settings["Auth__PublicOrigin"],
    site_config[0].application_stack,
  ]
}
```

So Deploy never arms, disarms or rolls back the hosted studio, and never replaces the image Publish chose.

The site also sets its own response headers, rate limits and body ceilings in code, with no app setting to turn them off: `nosniff`, `no-referrer`, `X-Frame-Options: DENY` and a Content-Security-Policy on every response, a 32 MB default request body (raised to 324 MB for a submit and 512 MB for a vision video upload), and the per-creator limits above. The CSP names your storage account's blob host when `Storage__Backend` is `azure`, so video still plays when it is served from the account rather than the site.

Entra sign-in needs `Auth__ClientId`, `Auth__PublicOrigin`, a tenant and a client credential (`AZURE_CLIENT_ID` or `Auth__ClientSecret`). If one is missing the site stops at startup.

## Secrets

Keep secrets out of app settings and files. Use Key Vault for anything sensitive, such as `Auth--ClientSecret`. Set `key_vault_uri` so Terraform adds `KeyVault__Uri`, and set `key_vault_id` so the portal identity gets Key Vault Secrets User on that vault. The vault must use RBAC authorization and be reachable over a private endpoint from the web app.

An `ApiKey` for the video helper follows the same route. Terraform writes a Key Vault reference (`@Microsoft.KeyVault(SecretUri=...)`) into `Agent__ApiKey`, and App Service resolves it through the portal identity.

## Checking a live site

`GET /healthz` returns 200 without a session. `GET /api/status` needs a sign-in, and Publish checks that: it expects HTTP 401 without one and fails when the site answers without sign-in.

If a setting is missing or malformed, the startup log names it. But a site that restarts in a loop is almost always a missing or badly formed `AzureMl__*` or `Auth__*` value, or a `WEBSITES_PORT` that is not `8080`. [Troubleshooting](./guides/troubleshooting.mdx) has the log commands.

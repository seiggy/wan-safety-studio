The studio now runs across three boundaries. The release scripts in `scripts/release` build, promote and deploy, in bash
or PowerShell, from any machine on the studio's network; the GitHub Actions workflows are an example of running them in CI.
The .NET server in App Service runs the lifecycle (Start, Stop, release selection). Azure ML jobs run the Python and ComfyUI
containers.

Check [Prerequisites](../prerequisites.mdx) first. This page lists the order and the approvals. The release scripts, their
prerequisites and every option are in [Release scripts](./release-scripts.mdx). The foundation workflow, the example GitHub
environments and the recovery path are in [Protected private pipelines](./private-pipelines.mdx).

## Approvals

Nothing that costs money or changes identity runs without an explicit approval.

| Approval | Where | What you are approving |
| --- | --- | --- |
| Foundation plan review | Your Terraform pipeline, or whoever runs `terraform apply` | Applying a reviewed plan. Resources that bill while the GPU is off appear in it: Premium registry, private endpoints, storage, the App Service plan. Role assignments appear in it too. |
| Publisher identity | The build and promote scripts sign in as `Pipeline:PublisherPrincipalId` | Building an artifact and publishing it to regions. Whoever can sign in as that principal can release. |
| Site change rights | The deploy-server script | Pointing the App Service at a verified server artifact. |
| GPU spend confirmation | Administration page, Start | Variable Spot GPU cost, one node at most per region. |
| Customer network confirmation | Administration page, Start | That your security team applied the exported NSG rules, when a customer-managed NSG is used. It is an acknowledgment. The host does not verify the rules. |
| Tenant administration | Outside the pipeline | Entra registration and consent. See [Entra sign-in bootstrap](#bootstrap-entra-sign-in). |

If you automate with the example GitHub workflows, their `studio-plan`, `studio-apply`, `studio-build`, `studio-publish`
and `studio-server` environments add a reviewer approval to each stage. The environments need required reviewers and runner-group restrictions
that an owner configures in GitHub. The workflow files cannot create or prove those settings.

## Before you start

1. Decide how you will create the foundation ([three ways](#deploy-the-foundation)). With the repo Terraform, fill in the
   customer input ([variables](../terraform-variables.mdx)) and keep it outside Git. Set `compute_enabled` to `false`;
   `true` is rejected.
2. Ask the network owner to confirm the six DNS zones per region are linked, each GPU subnet is dedicated with
   `defaultOutboundAccess` off, and the shared host subnet is delegated.
3. Choose the machine that runs the release scripts: one that resolves your private DNS zones and reaches the private
   endpoints, with a container engine (Docker, Podman or `wslc`). See [Release scripts](./release-scripts.mdx#prerequisites).
   Public CI-hosted agents cannot reach the private endpoints.
4. Run the offline checks from a clean checkout if you changed anything in `infra\`:

```powershell
pwsh -NoProfile -File infra\tests\Export-MockedContracts.ps1
python -m unittest discover -s infra -p 'test_*.py' -v
```

Do not run these from a directory that holds customer `tfvars` or state.

## Deploy the foundation

The foundation is the set of durable, private Azure resources every later stage writes to or reads from. Per region: a
resource group, an Azure ML workspace, two user-assigned identities, a storage account with three containers, a Premium
container registry, a Key Vault, Application Insights, private endpoints and the GPU subnet's NSG. Once, in the control
region: the App Service that hosts the studio. Plus the role assignments that let the site, the GPU jobs, the operator and
the publisher use them. It creates no GPU: compute, and the optional NAT gateway and public IP, are created by Start in
Administration and removed by Stop. The network itself (VNets, subnets, private DNS zones and their links, Log Analytics)
is yours, and the foundation only references it. The full inventory is in [Resources](../resources.mdx).

Create it in one of three ways. All three end at the same place: the [values later stages need](#values-the-later-stages-need).

### Option 1: the repo Terraform, from your pipeline or by hand

`infra\` is a Terraform root (1.9 or later, below 2.0; the lock pins AzureRM 5.6.0 and AzAPI 2.12.0). It has no backend
block, so it never picks up state by accident. Keep your input and state outside the checkout:

1. Copy `infra\terraform.tfvars.json.example` outside the checkout and fill it in. Every field is described in
   [Terraform variables](../terraform-variables.mdx). Set `publisher_principal_id` to the identity that will run the
   release scripts, and `operator_principal_id` to the operator who runs Start, Stop and recovery.
2. Copy `infra\*.tf`, `infra\.terraform.lock.hcl` and `infra\modules` into a working folder, and add a `backend.tf` for
   your state, for example a private storage account with Entra auth:

```hcl title="backend.tf (in your working folder, not in the repo)"
terraform {
  backend "azurerm" {}
}
```

3. Sign in to Azure CLI with an identity that can create the resources and their role assignments. Contributor alone cannot
   write role assignments; pair it with User Access Administrator or Role Based Access Control Administrator at the
   deployment scope. Then plan, review and apply:

```bash title="bash"
terraform -chdir=$WORK init -input=false -lockfile=readonly -backend-config=$HOME/wan/backend.hcl
terraform -chdir=$WORK plan -input=false -var-file=$HOME/wan/foundation.tfvars.json -out=foundation.tfplan
terraform -chdir=$WORK show foundation.tfplan     # review it, including the role assignments
terraform -chdir=$WORK apply -input=false foundation.tfplan
```

```powershell title="PowerShell"
terraform -chdir=$work init -input=false -lockfile=readonly -backend-config=$HOME\wan\backend.hcl
terraform -chdir=$work plan -input=false -var-file=$HOME\wan\foundation.tfvars.json -out=foundation.tfplan
terraform -chdir=$work show foundation.tfplan     # review it, including the role assignments
terraform -chdir=$work apply -input=false foundation.tfplan
```

In your own CI, run the same commands with a plan job and a separately approved apply job that applies the saved plan.
Review every plan before you apply it, and refuse one that deletes or replaces anything: the routine path never needs a
delete. On state from a pre-migration deployment, follow the verified-OFF migration in `infra\README.md` first.

4. Read the outputs. They are informational: Terraform sets no application settings and emits no contract, so you copy
   the values by hand.

```bash
terraform -chdir=$WORK output -json regions      # per region: workspace, identities, storage, registry, vault, NSG, tags
terraform -chdir=$WORK output -json portal       # the site's ID, host names and identity
terraform -chdir=$WORK output -json gpu_nsg_rules
```

If you use a customer-managed NSG, send `gpu_nsg_rules` to the security team.

### Option 2: the example GitHub Actions workflow

`.github/workflows/foundation.yml` is an example of Option 1 in GitHub Actions. Its plan job (environment `studio-plan`)
saves a binary plan and its JSON in a private artifact container and rejects any delete or replacement; its apply job
(environment `studio-apply`) applies that exact plan after a separate approval. It runs only on self-hosted runners labelled
`wan-private` with a federated identity per environment, and reads its inputs from `STUDIO_TFVARS_*` and `STUDIO_BACKEND_*`,
so it will not run in your repository as is. Use it as a template for your own pipeline. See
[Protected private pipelines](./private-pipelines.mdx).

### Option 3: your own tooling (Bicep, Pulumi, the portal)

You can create the resources any way you like, as long as they match what the studio checks at run time. Use
[Resources](../resources.mdx) as the inventory and `infra\modules\region` as the specification. Per region, the studio and
the scripts require:

| Resource | Required properties |
| --- | --- |
| Azure ML workspace | Public network access off, identity-based system datastores, the workspace identity below as its primary identity, and the storage account, registry and Key Vault below linked to it. Two identity-auth AzureBlob datastores: `wan_blob` on `wan-studio` and `wan_release` on `wan-release`. |
| Workspace identity | User-assigned. Used by the workspace for its storage, vault and registry. |
| GPU (compute) identity | User-assigned. The identity GPU jobs run as. |
| Storage account | Public access off, shared key off, no blob public access, TLS 1.2. Private containers `wan-studio`, `wan-release` and `wan-control`. |
| Container registry | Premium, admin user off, anonymous pull off, public access off, trusted Azure services allowed (promotion uses `az acr import`). |
| Key Vault | RBAC authorization, purge protection, public access off. |
| Private endpoints | Blob, file, vault, registry and the workspace (`amlworkspace`), in your private endpoint subnet, registered in your six private DNS zones (blob, file, vault, registry, the Azure ML API and notebooks). |
| GPU subnet and NSG | A dedicated subnet with default outbound access off and no delegation, and an NSG on it: yours, or one with the rules in `infra\modules\region\network-security.tf`. |
| Ownership tags | `application=wan-safety-studio`, `deployment=<deployment name>`, `managedBy` and `region` on every studio-owned resource. The studio refuses to change anything that does not carry them. |

Once, in the control region: an App Service (Linux, one worker, HTTPS only, public access off, VNet integration with image
pull over the VNet, a user-assigned identity that pulls from the registry, health check `/healthz`) and its private endpoint
in `privatelink.azurewebsites.net`.

Role assignments, for the site identity, the GPU identity, the workspace identity, the operator and the publisher, are listed
in [Identity and security](../architecture/identity-and-security.mdx). The custom roles are defined in
`infra\operations-rbac.tf` and `infra\modules\region\foundation.tf`; create equivalents with the same actions.

### Values the later stages need

Whichever option you used, record these. They fill the site's application settings
([Configuration](../configuration.mdx#configure-the-site)) and the settings document that the release scripts read: the same
`Studio` section, plus a `Pipeline` section ([Pipeline settings](./private-pipelines.mdx#pipeline-settings)). "Terraform"
names the key in `terraform output -json regions` (per region) or `terraform output -json portal`.

The examples are made up but have the exact shape the studio expects: deployment `wan-cus`, region `centralus` and the
eight-hex name suffix `1a2b3c4d` that Terraform derives. Three kinds of value are easy to mix up:

- **GUID**: a bare `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`. Tenants, subscriptions, object IDs and client IDs are all GUIDs,
  and each field says which one it wants. A managed identity has both an **object (principal) ID** and a **client ID**; they
  are different GUIDs. `az identity show --ids <identity resource ID> --query "{clientId:clientId, objectId:principalId}"`
  prints both.
- **Resource ID**: the full ARM path that starts with `/subscriptions/`. Every field ending in `Id` that is not a GUID is
  one. In the tables, `…` stands for `/subscriptions/22222222-2222-2222-2222-222222222222/resourceGroups`; the
  [complete example](#example-settings-document) has every ID in full.
- **Host name**: a DNS name only, no `https://` and no path.

| `Studio:DeploymentName` | `wan-cus` | Lowercase name. Terraform: your `deployment_name`. Used by the site and ownership checks. |
| `Studio:ControlRegion` | `centralus` | Region key; one of the keys under `Studio:Regions`. Terraform: your `control_region`. Used by build, deploy-server and the site. |

endpoint's **DNS configuration** rather than building it.

### DNS for the site

With `portal` set, give the DNS owner the private endpoint IP so creators and administrators can resolve both hostnames:

```powershell
az network private-endpoint show -g <studio-resource-group> -n pe-<stem>-portal `
  --query "customDnsConfigs[].{fqdn:fqdn,ip:ipAddresses[0]}" --output table
```

Both `app-<stem>.azurewebsites.net` and `app-<stem>.scm.azurewebsites.net` must resolve to that IP from the machine that runs
the release scripts and from creator machines. The server deployment checks that the site host resolves privately and stops if it does not.

## Configure the site

The studio settings come from the foundation. Set the `Studio__*` application settings (regions, resource IDs, policy ceilings) on the App Service site as
described in [Configuration](../configuration.mdx#configure-the-site), and restart it. A wrong value does not stop the site: it starts, answers `/api` with 503 and serves `/health-ui`, which names the settings to fix ([Configuration](../configuration.mdx#when-a-setting-is-wrong)). Open `https://<site>/health-ui` until it reports `ready`. The Administration page then edits the live limits within those ceilings.

## Bootstrap Entra sign-in

The site signs users in with its own Entra app registration (OpenID Connect authorization code flow with PKCE; App Service
Authentication is not used). It needs four things in your tenant, done once after the foundation exists:

| What | Value the code expects |
| --- | --- |
| App registration | Single tenant. Web redirect URI `https://<site host>/auth/callback`. Microsoft Graph delegated `openid` and `profile`, nothing else. |
| App roles | `VideoCreator` (create videos) and `StudioAdmin` (Administration: release selection, Start, Stop, settings). Value strings exactly as written, allowed member type User. |
| Assignments | The enterprise application with **Assignment required** on, and a group (or users) assigned to each role. A user with neither role is refused. |
| Client credential | A federated credential that trusts the site's managed identity, so there is no secret. Issuer `https://login.microsoftonline.com/<tenant id>/v2.0`, subject the identity's **object (principal) ID**, audience `api://AzureADTokenExchange`. |

Then the site gets two application settings: `Auth__ClientId` (the registration's application ID) and `Auth__PublicOrigin`
(`https://<site host>`, lowercase, no path or port). `Auth__TenantId` defaults to `Studio__TenantId`, and `AZURE_CLIENT_ID`
(the site identity's client ID, already set in [Configure the site](#configure-the-site)) is what signs the federated
assertion. `Auth__Mode` defaults to `Entra` outside Development.

You need an Entra role that can create app registrations and grant tenant-wide consent: Cloud Application Administrator,
Application Administrator or Global Administrator. Use the Azure CLI or the portal. You need the site's host name
and managed identity, from Terraform (`terraform output -json portal`: `hostname`, `identityPrincipalId`,
`identityClientId`) or from the portal (the web app, and the `id-<stem>-portal` managed identity).

:::tip Names are yours, role values are not
Name the app registration, the app roles, the groups and the federated credential whatever your users will recognise. Only
these must match exactly, because the site checks them:

- the app role **values** `VideoCreator` and `StudioAdmin`, case-sensitive (the `roles` claim must contain one of them);
- the redirect URI path `/auth/callback` on your site's host;
- the federated credential's issuer `https://login.microsoftonline.com/<tenant id>/v2.0`, subject (the site identity's
  object ID) and audience `api://AzureADTokenExchange`.
:::

```bash
TENANT=<tenant id>
SITE_HOST=app-<stem>.azurewebsites.net          # the hostname output, or your custom domain
SITE_IDENTITY_PRINCIPAL=<identityPrincipalId>    # object ID of id-<stem>-portal
SITE_RG=<resource group of the site>
SITE_NAME=app-<stem>

# Any names work for these; pick what your users will recognise.
APP_DISPLAY_NAME="WAN Safety Studio"
CREATOR_ROLE_DISPLAY_NAME="Video creator"
CREATOR_ROLE_DESCRIPTION="Create videos in the studio."
ADMIN_ROLE_DISPLAY_NAME="Studio administrator"
ADMIN_ROLE_DESCRIPTION="Select releases, start and stop regions, edit settings."
CREATORS_GROUP="WAN Safety Studio Creators"
ADMINS_GROUP="WAN Safety Studio Admins"
FEDERATED_CREDENTIAL_NAME="wan-studio-site"
az login --tenant "$TENANT"

# 1. App roles and the Graph openid/profile delegated permissions.
#    The "value" strings VideoCreator and StudioAdmin must stay exactly as written: the site checks them.
cat > roles.json <<EOF
[
  {"id": "$(uuidgen)", "value": "VideoCreator", "displayName": "$CREATOR_ROLE_DISPLAY_NAME", "description": "$CREATOR_ROLE_DESCRIPTION",
   "allowedMemberTypes": ["User"], "isEnabled": true},
  {"id": "$(uuidgen)", "value": "StudioAdmin", "displayName": "$ADMIN_ROLE_DISPLAY_NAME", "description": "$ADMIN_ROLE_DESCRIPTION",
   "allowedMemberTypes": ["User"], "isEnabled": true}
]
EOF
cat > graph.json <<'EOF'
[{"resourceAppId": "00000003-0000-0000-c000-000000000000", "resourceAccess": [
  {"id": "37f7f235-527c-4136-accd-4a02d197296e", "type": "Scope"},
  {"id": "14dad69e-099b-42c9-810b-d002981feec1", "type": "Scope"}]}]
EOF

# 2. The registration: single tenant, web redirect URI (the /auth/callback path is fixed)
APP_ID=$(az ad app create --display-name "$APP_DISPLAY_NAME" --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "https://$SITE_HOST/auth/callback" \
  --app-roles @roles.json --required-resource-accesses @graph.json --query appId -o tsv)

# 3. Trust the site's managed identity instead of a secret (issuer, subject and audience are fixed)
az ad app federated-credential create --id "$APP_ID" --parameters "{
  \"name\": \"$FEDERATED_CREDENTIAL_NAME\", \"issuer\": \"https://login.microsoftonline.com/$TENANT/v2.0\",
  \"subject\": \"$SITE_IDENTITY_PRINCIPAL\", \"audiences\": [\"api://AzureADTokenExchange\"]}"

# 4. Enterprise application with assignment required, and admin consent for openid and profile
SP_ID=$(az ad sp create --id "$APP_ID" --query id -o tsv)
az ad sp update --id "$SP_ID" --set appRoleAssignmentRequired=true
az ad app permission admin-consent --id "$APP_ID"

# 5. Groups, members and role assignments
CREATORS=$(az ad group create --display-name "$CREATORS_GROUP" --mail-nickname wan-studio-creators --query id -o tsv)
ADMINS=$(az ad group create --display-name "$ADMINS_GROUP" --mail-nickname wan-studio-admins --query id -o tsv)
az ad group member add --group "$CREATORS" --member-id "$(az ad user show --id creator@contoso.com --query id -o tsv)"
az ad group member add --group "$ADMINS" --member-id "$(az ad user show --id admin@contoso.com --query id -o tsv)"
for pair in "$CREATORS:VideoCreator" "$ADMINS:StudioAdmin"; do
  ROLE_ID=$(az ad app show --id "$APP_ID" --query "appRoles[?value=='${pair#*:}'].id" -o tsv)
  az rest --method POST --uri "https://graph.microsoft.com/v1.0/servicePrincipals/$SP_ID/appRoleAssignedTo" \
    --body "{\"principalId\": \"${pair%%:*}\", \"resourceId\": \"$SP_ID\", \"appRoleId\": \"$ROLE_ID\"}"
done

# 6. Tell the site
az webapp config appsettings set -g "$SITE_RG" -n "$SITE_NAME" --settings \
  "Auth__ClientId=$APP_ID" "Auth__PublicOrigin=https://$SITE_HOST"
```

1. **Identity** > **Applications** > **App registrations** > **New registration**. Name: anything your users will recognise,

   - the admin role, for example display name `Studio administrator`, value `StudioAdmin`.

   then **Grant admin consent for** your tenant.

   **Name** is yours to choose; the rest is fixed: issuer `https://login.microsoftonline.com/<tenant id>/v2.0`, type **Explicit subject identifier**, value the object
   (principal) ID of the `id-<stem>-portal` managed identity (Azure portal > the identity > **Overview** > **Object
   (principal) ID**), audience `api://AzureADTokenExchange`. Do not create a client secret.

   required?** **Yes**, **Save**.

   and `WAN Safety Studio Admins`), with their members. Keep the admins group small.

   assign users directly.
8. In the Azure portal, the web app > **Settings** > **Environment variables** > **App settings**: add

An administrator who should also create videos needs both roles: put them in both groups. If your organization requires a
client secret instead of the federated credential, store it in Key Vault and set `Auth__ClientSecret` to a Key Vault

1. Open `https://<site host>/health-ui`. It must report `ready` with no `Auth` issues.
2. Browse to `https://<site host>/` and sign in as a member of the admins group. The **Administration** page is listed.

## Build and promote the GPU release

Run the build script, then the promote script, from the root of a clean checkout on a machine that meets the
[prerequisites](./release-scripts.mdx#prerequisites):

- **Identity.** Azure CLI must be signed in as `Pipeline:PublisherPrincipalId`: a service principal, a managed identity, or
  your own account if you set that value to your object ID. The scripts check it before any work. Pick the sign-in with
  `--login` / `-Login`.
- **Network.** The machine must resolve the studio's private DNS zones and reach every region's registry, storage and
  Azure ML endpoints on port 443. The scripts check each one first.
- **Container engine.** The build needs Docker (with `buildx`), Podman or `wslc`, passed with `--container-engine` /
  `-ContainerEngine`. Promotion runs no container.
- **Inputs.** The GPU build fetches the pinned upstream commit from github.com and about 45 GB of pinned model weights from
  huggingface.co, and verifies every size and hash. To fetch them once, pass persistent cache folders, as described in
  [GPU build inputs](./hosted-lifecycle.mdx#gpu-build-inputs-optional-caches).

```bash title="bash"
scripts/release/build-artifact.sh --settings ~/wan/settings.json --container-engine podman \
  --model-cache /srv/wan/models --license-cache /srv/wan/licenses --upstream-source /srv/wan/upstream
scripts/release/promote-release.sh --settings ~/wan/settings.json --artifact <release artifact id>
```

```powershell title="PowerShell"
./scripts/release/Build-StudioArtifact.ps1 -Settings ~/wan/settings.json -ContainerEngine Wslc `
  -ModelCache D:\wan\models -LicenseCache D:\wan\licenses -UpstreamSource D:\wan\upstream
./scripts/release/Publish-StudioRelease.ps1 -Settings ~/wan/settings.json -Artifact <release artifact id>
```

The build builds the GPU image to a private unready tag, runs a CPU probe against its exact digest, verifies the model and
licence snapshot and seals an immutable artifact. It ends by printing the **Release artifact ID** (64 hex characters) and
the promote command to run next.

Promotion publishes that ID to every configured region, or only to the regions you pass. For each region it copies the image
by digest, verifies every blob, registers the Azure ML assets, and writes the create-only regional binding last, so a partly
promoted region stays unavailable. It allocates no GPU. If a region fails, the others still complete, and rerunning the same
ID is safe. The report repeats the Release artifact ID with the regions it reached and tells you what to do in
Administration. See [The Release artifact ID](#the-release-artifact-id).

The model set is about 41.6 GiB, so promotion needs private bandwidth and temporary disk. The full walkthrough, the options
and the output are in [Release scripts](./release-scripts.mdx#build-and-promote-the-gpu-release). To run the same steps in
GitHub Actions, see the example `release.yml` and `promote.yml` in
[Automate with GitHub Actions](./release-scripts.mdx#automate-with-github-actions).

## Build and deploy the server

Run the deploy-server script with `--build`. It builds and seals the server image, then deploys it by registry digest. It
never arms submission. It points the site at the image, waits for `/healthz`, and confirms `/api/status` answers 401 without
a sign-in. If that check fails, it stops the site. The site must already have `Auth__ClientId` and `Auth__TenantId`
([Bootstrap Entra sign-in](#bootstrap-entra-sign-in)) and `AzureMl__Armed=false`.

```bash title="bash"
scripts/release/deploy-server.sh --settings ~/wan/settings.json --build --container-engine docker
```

```powershell title="PowerShell"
./scripts/release/Deploy-StudioServer.ps1 -Settings ~/wan/settings.json -Build -ContainerEngine Wslc
```

The script prints the **server artifact ID**. Keep it to redeploy the same image later with `--artifact` / `-Artifact`. It is
not the Release artifact ID: never paste it into Administration. Building checks the publisher identity like any build, and
the machine also needs to resolve the site's private hostname. See
[Release scripts](./release-scripts.mdx#build-and-deploy-the-server). The example `deploy-server.yml` workflow does the
deployment step in GitHub Actions.

Open `https://app-<stem>.azurewebsites.net/` from the VPN and sign in as a member of the creators group. The site is up and
generation is still refused.

## The Release artifact ID

The promote script's report ends with the Release artifact ID and the regions it reached. That ID is what Administration asks
for:

1. Sign in as a `StudioAdmin` and open **Administration**.
2. On the card of each promoted region whose phase is `Off`, paste the ID into **Release artifact ID** and choose
   **Select release**. The host verifies the build manifest, the regional binding and the Azure ML assets, then shows the ID
   as **Approved release**.
3. Repeat for each region. The same ID is used everywhere it was promoted.

Enter it only after promotion has written a binding for that region; before that, Select release is refused with "has not
been promoted" or "has no verified binding". A region that is not `Off` refuses it too: stop the region first. Select release
starts no compute and costs nothing. A server artifact ID, an image digest or a run ID is rejected. More,
including how to find the ID later, is in [The Release artifact ID](./release-scripts.mdx#the-release-artifact-id).

## Select a release and Start

Start is a hosted action. A person with the `StudioAdmin` role opens the Administration page, selects a promoted release for
a region by pasting the Release artifact ID ([above](#the-release-artifact-id)), and starts that region. Administration does not build
or promote anything; it only selects an already promoted release. The full walkthrough, including what to do when the ID is
lost, is in [Select a release](./hosted-lifecycle.mdx#select-a-release-where-the-artifact-id-comes-from). Start needs explicit confirmation of GPU spend. The host verifies the release, private
connectivity, the live price, the SKU and quota before its first write, then creates one private Spot node and arms the
region. [Hosted lifecycle](./hosted-lifecycle.mdx) lists every check.

Starting does not warm a GPU. The node is allocated when the first job arrives. See [Operate and stop](./operate-and-stop.mdx).

## Verify

Open Administration and read the region card. It shows the phase and the live Azure state. A region whose state cannot be
read shows `UNREADABLE`, never off; see [Fix a region that shows UNREADABLE](./hosted-lifecycle.mdx#fix-a-region-that-shows-unreadable). The card does not run a generation.

For an end-to-end check, start one region, generate one short clip from the Create page, and stop afterwards, even on
failure, to release the GPU. Stop works without the Python, Docker or Terraform tools. If the host itself is unavailable,
use [Independent recovery](./private-pipelines.mdx#independent-recovery).

The studio now runs across three boundaries. GitHub Actions on private runners builds, promotes and deploys. The .NET
server in App Service runs the lifecycle (Start, Stop, release selection). Azure ML jobs run the Python and ComfyUI
containers. No operator script performs deployment any more. The old `Invoke-WanSafetyStudio.ps1` Deploy, Prepare, Portal,
Publish and Start actions, `Initialize-PortalAuth.ps1` and the shell upload scripts are retired. See
[Retired tools](#retired-tools).

Check [Prerequisites](../prerequisites.mdx) first. This page lists the order and the approvals. The workflow inputs,
protected environments, runner requirements and recovery path are in [Protected private pipelines](./private-pipelines.mdx),
and are not repeated here.

## Approvals

Nothing that costs money or changes identity runs without an explicit approval.

| Approval | Where | What you are approving |
| --- | --- | --- |
| `studio-plan` environment | `foundation.yml`, plan job | Creating a saved, non-destructive plan in private storage. |
| `studio-apply` environment | `foundation.yml`, apply job | Applying that exact plan. Resources that bill while the GPU is off appear in it: Premium registry, private endpoints, storage, the App Service plan. |
| `studio-build` environment | `release.yml` | Building one server, GPU or trainer artifact. |
| `studio-publish` environment | `promote.yml` | Publishing a sealed artifact to every configured region. |
| `studio-server` environment | `deploy-server.yml` | Deploying a verified server artifact. |
| GPU spend confirmation | Administration page, Start | Variable Spot GPU cost, one node at most per region. |
| Customer network confirmation | Administration page, Start | That your security team applied the exported NSG rules, when a customer-managed NSG is used. It is an acknowledgment. The host does not verify the rules. |
| Tenant administration | Outside the pipeline | Entra registration and consent. See [Entra sign-in bootstrap](#bootstrap-entra-sign-in). |

The environments need required reviewers and runner-group restrictions that an owner configures in GitHub. The workflow
files cannot create or prove those settings.

## Before you start

1. Fill in the Terraform customer input ([variables](../terraform-variables.mdx)). Keep it outside Git, in
   `STUDIO_TFVARS_JSON` or `STUDIO_TFVARS_PATH`. Set `compute_enabled` to `false`; `true` is rejected.
2. Ask the network owner to confirm the six DNS zones per region are linked, each GPU subnet is dedicated with
   `defaultOutboundAccess` off, and the shared host subnet is delegated.
3. Check that the private runner group (`wan-private`) exists and resolves your private DNS. Public GitHub runners cannot
   reach the private endpoints.
4. Run the offline checks from a clean checkout if you changed anything in `infra\`:

```powershell
pwsh -NoProfile -File infra\tests\Export-MockedContracts.ps1
python -m unittest discover -s infra -p 'test_*.py' -v
```

Do not run these from a directory that holds customer `tfvars` or state.

## Deploy the foundation

Dispatch `foundation.yml` from the protected default branch. The plan job saves a binary plan and its JSON in the private
artifact container. Open that run's `reviewed.json` and review it, including the role-assignment changes, before you approve
`studio-apply`. The apply job applies the same saved plan without re-planning. Terraform produces infrastructure only: it emits no receipt and sets no application settings on the site.

The workflow rejects every delete or replacement. So it cannot be used on state from a pre-migration deployment. For that,
follow the verified-OFF migration in `infra\README.md` first, and see [Terraform variables](../terraform-variables.mdx).

After a successful apply, configure the site. Copy the resource IDs of what Terraform created (and your landing-zone IDs) into the
App Service application settings, following [Configuration](../configuration.mdx#configure-the-site), and put the same
values into the settings document the pipelines read (`STUDIO_SETTINGS_JSON` or `STUDIO_SETTINGS_PATH`). Nothing updates either
for you. Keep the last known-good settings document outside Git.

If you use a customer-managed NSG, send the rules in the `gpu_nsg_rules` Terraform output to the security team. Someone with
access to the state backend can read it:

```powershell
terraform -chdir=infra output -json gpu_nsg_rules
```

### DNS for the site

With `portal` set, give the DNS owner the private endpoint IP so creators and administrators can resolve both hostnames:

```powershell
az network private-endpoint show -g <studio-resource-group> -n pe-<stem>-portal `
  --query "customDnsConfigs[].{fqdn:fqdn,ip:ipAddresses[0]}" --output table
```

Both `app-<stem>.azurewebsites.net` and `app-<stem>.scm.azurewebsites.net` must resolve to that IP from the runner and from
creator machines. The server deployment workflow checks that the site host resolves privately and stops if it does not.

## Configure the site

The studio settings come from the foundation. Set the `Studio__*` application settings (regions, resource IDs, policy ceilings) on the App Service site as
described in [Configuration](../configuration.mdx#configure-the-site), and restart it. A wrong value does not stop the site: it starts, answers `/api` with 503 and serves `/health-ui`, which names the settings to fix ([Configuration](../configuration.mdx#when-a-setting-is-wrong)). Open `https://<site>/health-ui` until it reports `ready`. The Administration page then edits the live limits within those ceilings.

## Bootstrap Entra sign-in

An identity owner does this once, by hand, after the foundation exists because the federated credential needs the site
identity's principal ID. Nothing in the pipeline or the web host holds tenant-administrator rights, and no client secret is
created. Follow `docs\operations\entra-bootstrap.md`. It creates the single-tenant registration, the `VideoCreator` and
`StudioAdmin` roles, the groups, the federated credential and the admin consent for `openid` and `profile`.

When it is done, give the site `Auth__ClientId` (the registration's client ID), `Auth__PublicOrigin` (the site's HTTPS origin,
lowercase, no path or port) and `Auth__TenantId` as ordinary app settings, with the rest of the site's settings. The
server deployment workflow refuses to run until `Auth__ClientId` is set and `Auth__TenantId` matches the tenant. See
[Identity and security](../architecture/identity-and-security.mdx) and [Configuration](../configuration.mdx).

## Build and promote the GPU release

Dispatch `release.yml` with component `gpu`. It builds the GPU image to a private unready tag, runs a CPU probe against its
exact digest, verifies the model and licence snapshot, and seals an immutable artifact. The GPU build does not download
weights: the model and licence caches must already exist on the runner. Before the first run, set up the three cache folders and the repository variables `STUDIO_UPSTREAM_SOURCE`, `STUDIO_MODEL_CACHE` and `STUDIO_LICENSE_CACHE` as described in [Prepare the GPU build caches](./hosted-lifecycle.mdx#prepare-the-gpu-build-caches-one-time-per-runner). Note the 64-character artifact ID it reports.

Then dispatch `promote.yml` with component `gpu` and that artifact ID. It promotes to every configured region. For each
region it verifies the registry digest and every blob, registers the Azure ML assets, and writes the create-only regional
binding last, so a partly promoted region stays unavailable. Promotion allocates no GPU. The ID you note here is the value
the Administration page asks for as **Release artifact ID**. To find it again later, see
[Select a release](./hosted-lifecycle.mdx#select-a-release-where-the-artifact-id-comes-from).

The model set is about 41.6 GiB, so promotion needs private bandwidth and temporary disk on the runner. If a region fails,
the others still complete. Details, the artifact layout and the retry behavior are in
[Protected private pipelines](./private-pipelines.mdx#immutable-promotion). There is one promotion path. The shell upload
scripts are gone.

## Build and deploy the server

Dispatch `release.yml` with component `server`, then `deploy-server.yml` with the server artifact ID. The deployment is by
registry digest only. It never builds and never arms submission. It points the site at the image, waits for `/healthz`, and confirms `/api/status` answers 401 without a sign-in. If that check
fails, the workflow stops the site.

Open `https://app-<stem>.azurewebsites.net/` from the VPN and sign in as a member of the creators group. The site is up and
generation is still refused.

## Select a release and Start

Start is a hosted action. A person with the `StudioAdmin` role opens the Administration page, selects a promoted release for
a region by pasting the GPU build artifact ID from the previous step, and starts that region. Administration does not build
or promote anything; it only selects an already promoted release. The full walkthrough, including what to do when the ID is
lost, is in [Select a release](./hosted-lifecycle.mdx#select-a-release-where-the-artifact-id-comes-from). Start needs explicit confirmation of GPU spend. The host verifies the release, private
connectivity, the live price, the SKU and quota before its first write, then creates one private Spot node and arms the
region. [Hosted lifecycle](./hosted-lifecycle.mdx) lists every check. Nothing here has been run against Azure.

Starting does not warm a GPU. The node is allocated when the first job arrives. See [Operate and stop](./operate-and-stop.mdx).

## Verify

Open Administration and read the region card. It shows the phase and the live Azure state. A region whose state cannot be
read shows `UNREADABLE`, never off; see [Fix a region that shows UNREADABLE](./hosted-lifecycle.mdx#fix-a-region-that-shows-unreadable). The card does not run a generation.

For an end-to-end check, start one region, generate one short clip from the Create page, and stop afterwards, even on
failure, to release the GPU. Stop works without the Python, Docker or Terraform tools. If the host itself is unavailable,
use [Independent recovery](./private-pipelines.mdx#independent-recovery).

## Retired tools

These files no longer exist, or accept no deployment action. Do not look for them, and treat any copy in an old runbook as
out of date.

| Retired | Replacement |
| --- | --- |
| `Invoke-WanSafetyStudio.ps1` Deploy | `foundation.yml` |
| `Invoke-WanSafetyStudio.ps1` Prepare, `upload-wan-code.sh`, `upload-wan-models.sh` | `release.yml` (gpu), then `promote.yml` |
| `Invoke-WanSafetyStudio.ps1` Publish | `release.yml` (server), then `deploy-server.yml` |
| `Invoke-WanSafetyStudio.ps1` Start | Administration page, `StudioAdmin` role |
| `Initialize-PortalAuth.ps1` | Manual runbook, `docs\operations\entra-bootstrap.md` |
| `Initialize-LocalDev.ps1` | A hand-written, git-ignored `appsettings.Development.json`. See `docs\local-generation.md`. |
| The `azureml\` folder | GPU build code in `build\gpu`, and the pipeline tools in `scripts\ci`. |
| `Install-GitHooks.ps1`, `Update-Docs.ps1` | Not part of deployment. No replacement is needed to deploy. |

`scripts\Invoke-WanSafetyStudio.ps1` still exists as a frozen legacy tool. It accepts only `-Action Status`,
`-Action Stop` and `-Action Check`, and rejects everything else. It is for the emergency release of a deployment that has
not been migrated. It will be deleted after the migration is verified. See [Operate and stop](./operate-and-stop.mdx#emergency-release).

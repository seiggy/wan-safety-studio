## Who does what

The .NET server in App Service runs Start, Stop and status. A person with the `StudioAdmin` role uses the Administration page
in the web UI, which calls the `/api/studio/*` routes. [Hosted lifecycle](./hosted-lifecycle.mdx) describes the routes, the
durable fence and every check. This page covers the day-to-day view.

Operators no longer run a script for Start. The host does not run Terraform, Docker or Python, so Stop works without them.
Building and promoting releases are workflows, covered in [Update and redeploy](./update-and-redeploy.mdx).

## The submission fence

Generation is off by default. The gate is a durable record per region in the control region's private `wan-control`
container, not an app setting. Each region is `off`, `starting`, `armed`, `stopping` or `unknown`, and only `armed` allows
generation for that region. If the record is missing or stale, nothing is submitted. A host with `Studio:Regions` ignores the
old `AzureMl__Armed` setting.

| Action | Compute | Gate |
| --- | --- | --- |
| Foundation apply | No compute is created or owned by Terraform | Not touched |
| Select release | Unchanged | Read and verify only |
| Start | One private Spot compute cluster (at most one node) is created for the region | `armed` after verification |
| Stop | Deleted with its underlying resources, plus the studio's own NAT and public IP | Closed first, `off` once release is proven |

## Start

Open Administration, select a promoted release for the region, and start it. Start needs explicit confirmation of GPU spend.
When a customer-managed NSG is in use, it also needs the customer network confirmation.

Start refuses before its first write when any of these fails:

- The release does not match its manifest, regional binding or live registrations.
- The workspace or the dedicated GPU subnet does not match the expected tags and settings.
- A private endpoint hostname does not resolve privately or does not answer on 443.
- A queued or running job could still resume.
- The live Linux pay-as-you-go price is above the regional `max_payg_hourly_usd`, the SKU is restricted, or Spot or family quota is short.
- The region is `unknown`. Stop must prove release first.

Price, SKU and quota are eligibility checks. They do not guarantee capacity, and the price threshold is a safety check, not
a billing cap.

The compute is the Linux Spot (`LowPriority`) `Standard_NC24ads_A100_v4`, minimum 0 and a maximum of one node, with a
120-second idle scale-down, no public node IP and SSH off. There is no dedicated, larger or serverless fallback. Start does
not warm a GPU. The cluster scales from zero when the first job arrives, which can take several minutes. Each job runs on
one instance. A per-job maximum is enforced on the server. The deployed policy is 120 minutes, and a region can be set lower
by an administrator, never higher.

## Stop

Stop in Administration releases every region and proves it. In order, per region, it:

1. Closes the fence, and cancels an in-flight Start.
2. Cancels relevant jobs.
3. Deletes only the studio's own compute with `underlyingResourceAction=Delete` and waits for absence.
4. Proves every relevant job is terminal.
5. Detaches only the studio's own NAT, deletes only its NAT and public IP, and verifies.

A foreign resource is an error, never adopted. A cancellation error is a warning only when fresh reads later show every job
terminal. Success needs every region released and the durable state recorded. Repeating Stop is safe. Because Stop does
not need Terraform, there is no state to reconcile afterwards.

Stop ends the GPU and NAT charges. It does not take the Azure bill to zero. The registry, private endpoints, storage, the
App Service plan and logging continue. See [Compute and cost](../architecture/compute-and-cost.mdx).

## Emergency release

When the host cannot be reached, or you want a release that does not depend on it, use
`scripts\recovery\Stop-Studio.ps1`. The `recover.yml` workflow runs the same script on a private runner in the
`studio-recovery` environment. It needs PowerShell, the Azure CLI, the shipped JSON schema and ARM access, and no Python,
.NET SDK, Terraform, Docker or fresh Terraform output.

```powershell
pwsh -NoProfile -File scripts\recovery\Stop-Studio.ps1 `
  -SettingsPath <outside-git-settings.json>
```

Sign in with the Azure CLI and select the right tenant and subscription first. The script checks scope and ownership before
it changes anything, stops the shared host, attempts every region, and returns failure for any partial release. It never
reports `VERIFIED OFF` unless every region proves release. Quiesce other deployment and operational writers first, because
there is no cross-operation lock between the pipelines and this script. The host stays stopped afterwards. Restart it as a
separate decision, and use Stop from the host so it records `off`. See
[Independent recovery](./private-pipelines.mdx#independent-recovery).

### A deployment that has not been migrated

A pre-migration (v1) deployment has no hosted lifecycle. For an emergency release only, the frozen legacy script still
works:

```powershell
.\scripts\Invoke-WanSafetyStudio.ps1 -Action Stop
.\scripts\Invoke-WanSafetyStudio.ps1 -Action Status
```

It accepts only `Status`, `Stop` and `Check`. It needs the old configuration and the preserved legacy v1 receipt (`foundation.json`) from that
deployment. Do not point it at a migrated regional deployment: it does not reconcile the new Terraform addresses. It is
deleted after the v1 to v2 migration is verified, and its offline test is `scripts\Test-LegacyLifecycle.ps1`.

## What the hosted site does at each step

| Action | Effect on the site |
| --- | --- |
| Start | Opens the fence for that region. Other regions are unchanged. |
| Stop | Closes the fence first, then releases compute. |
| Server deployment | Replaces the image and restarts the site. It never arms submission. |
| Release promotion | Writes new regional bindings. The host uses one only after you select it. |

Every site restart clears sign-in sessions, so creators sign in again. A restart also ends a batch that is still submitting.
Jobs already created in Azure ML continue. On restart the host turns `starting` and `stopping` into `unknown`, and does the
same for an `armed` region whose compute is gone, so check Administration after one. Do not scale the plan out. Sessions
live in process memory.

## Monitoring

### Region state

Administration shows, per region, the phase, selected and armed release, live compute and nodes, active jobs, owned egress,
blockers and the last error. A region that cannot be read shows `UNREADABLE`, not off. Treat any `unknown` as a reason to
run Stop.

### Jobs

Open the workspace in Azure ML studio and look at **Jobs**. For a failure after the job started, read the job's
`std_log.txt`. The studio's gallery and status page show the same jobs for creators. If a job sits in `Queued` or
`Preparing`, check Spot capacity and quota ([Troubleshooting](./troubleshooting.mdx)). A job that stays queued past the
queue wait is cancelled once and moved to the next eligible region only after fresh proof that it never started.

### Telemetry

Application Insights (`appi-<stem>`) is workspace-based and sends to the Log Analytics workspace you supplied. Query it
there. Ingestion bills against that workspace.

## Logs

The site container writes to standard output. Use the App Service log stream, or from a machine on the network:

```powershell
az webapp log tail -g <studio-resource-group> -n app-<stem>
```

The command goes through the private SCM endpoint, so the SCM hostname `app-<stem>.scm.azurewebsites.net` must resolve
privately. Turn on application logging to the file system first if the stream is empty. Downloading logs with
`az webapp log download` works but is slow.

A configuration problem does not stop the site. Open `https://<site>/health-ui` (anonymous) to see which settings are missing or invalid; `/api` answers 503 until they are fixed. See the [configuration page](../configuration.mdx#when-a-setting-is-wrong)
for what each setting should hold.

## Smoke test

A single generation from the studio proves the whole path. It needs a promoted release and a started region, so wrap it
with Start and Stop in Administration. Generate one short WAN clip from the Create page, confirm it in the Library, and
then stop, even if the generation failed. The server submits one instance with the region's job timeout and never
resubmits a created job. If the read-back of the job's limits does not match, the job is cancelled.

## Two artifacts, two triggers

The server and the GPU release are built independently, and their identifiers change for different reasons. Region,
deployment scope, mutable timeouts and workflow run IDs do not enter either one.

| Artifact | Identifier | Changes when | Workflows |
| --- | --- | --- | --- |
| Server image | 64-character artifact ID, the SHA-256 of a catalog record (schema, component, source commit, registry manifest digest) | The server or web source changes | `release.yml` (server), then `deploy-server.yml` |
| GPU release | 64-character sealed build artifact ID, from the strict build contract over code, models, licences and build inputs | Anything the GPU job depends on, listed below | `release.yml` (gpu), then `promote.yml` (gpu) |

The server is deployed by registry digest, never by tag. A GPU artifact is only promoted from a sealed build whose CPU
probe passed. Model snapshot names hash the sorted model records, so when only the adapter code or image changes, promotion
reuses the existing model snapshot and its Azure ML model. See
[Immutable promotion](./private-pipelines.mdx#immutable-promotion).

## What to run after a change

| You changed | Run |
| --- | --- |
| .NET server or React UI source only | `release.yml` (server), then `deploy-server.yml`. No GPU build. |
| GPU image inputs: `build\gpu` code, the shared model implementation, pins, profile or model manifests, or the licence records | `release.yml` (gpu), then `promote.yml` (gpu). Then an administrator selects the new release per region. |
| The trainer image | `release.yml` (yolox), then `promote.yml` (yolox). |
| The package feed for a build | A new build of the affected component. See [Prerequisites](../prerequisites.mdx#package-feeds-in-an-enterprise-environment). |
| Terraform files or the regional customer JSON | `foundation.yml`. Review the plan, then copy any changed resource ID into the site's `Studio__*` settings. See [Terraform variables](../terraform-variables.mdx). |
| `portal`, `agent`, `key_vault_*` or `feature_dataset_builder_enabled` | `foundation.yml`. Terraform sets no application settings, so change the matching `Agent__*`, `KeyVault__Uri` or `FEATURE_DATASET_BUILDER_ENABLED` setting on the site yourself. |
| `max_payg_hourly_usd`, `max_job_minutes`, `max_nodes` | The ceilings are `Compute__MaxPaygHourlyUsd`, `Compute__MaxJobMinutes` and `Compute__MaxNodes` in the site's `Studio__*` settings (and the settings document). Change them there and restart. Live concurrency, per-region timeout, priority and queue wait are changed in Administration, within those ceilings. |
| `compute_enabled` | Leave it `false`. `true` is rejected, because Terraform no longer creates compute. |
| Entra roles, groups, consent, redirect URI | The manual runbook, `docs\operations\entra-bootstrap.md`. Then update `Auth__ClientId` or `Auth__PublicOrigin` in the site's app settings if they changed. |
| A new hostname | Update DNS, the redirect URI and `Auth__PublicOrigin` together, then restart the site. |
| `deployment_name` | Treat it as a new deployment. Every name and the hash suffix change. |

## Rolling out a new GPU release

Promotion does not touch a running region. It writes new regional bindings, and the host uses a release only after an
administrator selects it. Selecting is refused unless the region is off, so the order is:

1. Dispatch `release.yml` with component `gpu`. Note the artifact ID.
2. Dispatch `promote.yml` with that artifact ID. Check that every region reports a binding. A region that failed has none
   and stays unavailable.
3. In Administration, stop the region if it is armed. Select the new release for the region.
4. Start the region with explicit spend approval.

Between a stop and the next start the region is off, so creators cannot submit jobs against a half-updated release.

## Rolling out a new server image

Dispatch `release.yml` with component `server`, then `deploy-server.yml` with its artifact ID. The workflow changes only the
site's image and restarts it. It never builds and never arms submission. It requires a set `Auth__ClientId` for the right tenant. It then waits for `/healthz` and checks that
`/api/status` answers 401 without a sign-in. If that check fails, it stops the site.

The restart clears every sign-in session and ends any batch that is still submitting. Jobs already created in Azure ML keep
running. After a restart the host marks a `starting` or `stopping` region `unknown`, so open Administration afterwards and
confirm each region's phase. Pick a quiet moment.

## When a release is stale

Promotion verifies the registry digest, every blob and the exact Azure ML registrations. Start verifies the selected
release against its manifest, regional binding and live registrations. If any of them has changed or is missing, Start
refuses before it writes anything. Rerun the promotion for that artifact. Retries are supported: it never overwrites an existing
asset, and it rechecks the content it reuses. No step downloads models on a GPU.

## Builds behind an authenticated feed

The pipeline reads feed credentials from optional runner paths: `STUDIO_NPMRC`, `STUDIO_NUGET_CONFIG` and `STUDIO_NETRC`.
They hold paths to protected user-level files, never credential values. Feed URLs and authentication for the GPU build go
through BuildKit secret mounts, so they do not land in an image layer. Use one approved feed per ecosystem. The variable
contracts are in `docs\operations\private-pipelines.md`. Check this on a non-production deployment before you rely on it.

## Terraform drift and plans

`foundation.yml` saves a plan and rejects every delete or replacement, including role assignments. A change that needs one,
such as the GPU role narrowing in the first migration, goes through the separate verified-OFF runbook in `infra\README.md`,
not the routine workflow. When policy changes something Terraform owns, such as a public IP tag, review the plan and resolve
the drift. Do not approve a plan you have not read, only to make the workflow pass.

Terraform sets no application settings on the site, so a foundation apply never reverts a server deployment or your settings. Running Terraform directly bypasses the
protected environments and the plan checks. Restrict who can do it.

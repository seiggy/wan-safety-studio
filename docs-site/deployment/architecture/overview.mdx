## Two groups of resources

The design splits Azure resources into two groups, and the split drives most of the safety checks in the host and the recovery script.

**Owned resources** are created and tagged by Terraform. Every one carries `application=wan-safety-studio`, `deployment=<deployment_name>` and `managedBy=terraform`. The host and the recovery script refuse to mutate a resource that lacks those tags. The tags (`Studio:Regions:<region>:OwnershipTags`) are the proof of ownership: before the studio creates, changes or deletes a compute, NAT gateway or public IP, or deletes anything at Stop, it requires them, so it can never touch a customer resource with a similar name or ID. Compute, and the NAT and public IP when managed egress is on, are created and deleted by the hosted lifecycle rather than Terraform, and carry ownership tags too.

**Supplied resources** belong to your landing zone: the GPU subnet, the private endpoint subnet, the six private DNS zones, the Log Analytics workspace, and optionally an NSG, a Key Vault and the App Service integration subnet with its DNS zone. Terraform reads them through data sources and variable IDs. It never takes ownership, and `terraform destroy` cannot touch them.

## The control path

The shared web app submits an Azure ML command job to the chosen region's workspace through the ARM API. The workspace schedules it on the `wan-gpu` cluster, which hosted Start created. The cluster scales from zero, so the first job in a session waits several minutes for a node. When the queue drains the node scales down after 120 seconds of idle time.

A job runs the promoted GPU image from the registry as the compute identity. It mounts the model folder and the workflow code read-only from the `wan_release` datastore, which it can read and not write, and writes its video under `video-library/` in the `wan-studio` container.

## The data path

Creators never receive Azure credentials. The site reads the gallery and streams videos itself through `/api/media/...`, using its own managed identity against the private blob endpoint. Uploaded reference images land under `studio/web-inputs/` and generated video under `video-library/`, both in the `wan-studio` container. The promoted code and models live in a second container, `wan-release`, which only the publisher and operator write and the site can only read for verification. Operational state, such as the submission fence and settings, lives in a third container, `wan-control`. See [Identity and security](./identity-and-security.mdx#release-assets-live-where-the-site-cannot-write-them).

## What is private and what is not

All data-plane services have public network access disabled: storage, Key Vault, the registry, the workspace and the web app. Reaching them takes a private endpoint and a DNS name that resolves to it. See [Networking](./networking.mdx).

Two paths still use Microsoft platform endpoints. The GPU cluster is a Batch-backed service, so its outbound rules allow Azure ML, Batch, Entra, ARM and Monitor service tags, not just your private endpoints. The web app reaches Entra ID and ARM through the App Service platform path (`vnet_route_all_enabled=false`). But neither makes the data stores public.

## Optional pieces

| Piece | Switch | What it adds |
| --- | --- | --- |
| Hosted web site | `portal` | App Service plan, web app, private endpoint, site identity and its role assignments |
| Owned egress | `manage_compute_egress` | Permission for hosted Start to create a NAT gateway and public IP and attach the NAT to the GPU subnet while compute exists |
| Customer NSG | `existing_gpu_nsg_id` | Swaps the owned NSG for yours; you apply the rules |
| Video helper | `agent` | `Agent__*` settings and an optional role on your Foundry resource |
| Key Vault configuration | `key_vault_uri`, `key_vault_id` | `KeyVault__Uri` and a Secrets User role for the site identity |

`compute_enabled` still exists but accepts only `false`. Terraform no longer creates compute.

## Landing-zone inputs

Only Azure public cloud and one subscription and tenant are supported. Each region you configure needs its own landing-zone inputs. The region names are your choice; there is no fixed region and no fixed count. All supplied resources must be in `subscription_id`, and each region's subnets must be in that region.

| Input | Variable (per region) | Notes |
| --- | --- | --- |
| Dedicated GPU subnet | `gpu_subnet_id`, `gpu_subnet_cidr`, `gpu_subnet_dedicated` | Only this studio may use it. `defaultOutboundAccess=false`, no delegation, no unrelated NAT. You must set `gpu_subnet_dedicated` to `true` explicitly. |
| Private endpoint subnet | `private_endpoint_subnet_id` | Distinct from the GPU subnet. |
| Six private DNS zones | `private_dns_zone_ids` | blob, file, vault, registry, api and notebooks, linked and resolvable from the runner, GPU and creator networks. |
| Log Analytics workspace | `log_analytics_workspace_id` | Application Insights is created against it. |
| GPU NSG (optional) | `existing_gpu_nsg_id` | Required when policy already attaches an NSG to the GPU subnet. |
| App Service subnet and zone (optional, one shared host) | `portal.subnet_id`, `portal.dns_zone_id` | Empty subnet delegated to `Microsoft.Web/serverFarms` in `control_region`, and `privatelink.azurewebsites.net`. |
| GPU egress | Routed egress, or `manage_compute_egress` | With `defaultOutboundAccess=false` the GPU nodes need a path to Azure service endpoints. |
| Private connectivity between regions | None (customer side) | The shared host and the private runners must reach every region's private endpoints. |
| Client DNS | None (customer side) | Creators and administrators must resolve the site hostname to the private endpoint. See [Networking](./architecture/networking.mdx). |

The network owner supplies these. The studio never creates or changes subnets, NSG rules on a customer NSG, route tables, DNS zones, DNS links or client DNS.

## Private runners

Build, promotion, foundation and server deployment run as GitHub Actions workflows on ephemeral Linux x64 runners labelled `wan-private`. The deployment owner sets up the runner group, the protected environments and the federated Azure identities. The workflow files cannot create or prove those settings. See [Protected private pipelines](./guides/private-pipelines.mdx) for the environments, the runner requirements and the variable contracts.

| Tool on the runner | Needed for |
| --- | --- |
| PowerShell 7.4 or later | The recovery script and the workflow steps |
| Azure CLI | Login and token acquisition |
| Docker and Buildx | Image builds and the CPU probe |
| Git | Source checkout |
| .NET 10 SDK and Python 3.12 | Supplied by GitHub setup actions |
| Terraform 1.16.6 | Foundation jobs, installed by the workflow. `infra\versions.tf` accepts 1.9 or later, below 2.0. The lock pins AzureRM 5.6.0 and AzAPI 2.12.0. |

Public GitHub runners do not supply private connectivity and must not be used.

## Tools on a developer or operator workstation

Deployment itself needs no workstation. You need these only to run the offline checks or the emergency release by hand.

| Tool | Version | Needed for |
| --- | --- | --- |
| PowerShell | 7.4 or later | `scripts\recovery\Stop-Studio.ps1`, `infra\tests\Export-MockedContracts.ps1`, `Test-StudioRecovery.ps1` |
| Azure CLI | Current | Login for the recovery script |
| Terraform | 1.9 or later, below 2.0 | Offline `infra\` checks |
| Git | Any | Source checkout |
| Python | 3.12 | `infra` and `scripts\ci` tests, and `build\gpu` unit tests |
| .NET 10 SDK | Current | `dotnet test tests\VideoSafetyStudio.Tests --artifacts-path .artifacts` |
| Docker | Linux containers | Only if you build images locally. Builds normally run on the private runner. |

GPU promotion needs substantial runner disk and bandwidth. The eight pinned model files alone are about 41.6 GiB, and by default the GPU build downloads them on every run, so the runner needs outbound HTTPS to github.com and huggingface.co. Optional cache variables make the build keep those files in a persistent folder: the first run fills it and later runs reuse it, as described in [GPU build inputs](./guides/hosted-lifecycle.mdx#gpu-build-inputs-optional-caches). Some of the models may require license acceptance or access approval from the model owner.

Local validation of the scripts and workflows was done on Windows only. The workflows target Linux x64 runners, and Linux and macOS execution has not been validated locally.

## Resource providers

Automatic registration is turned off on purpose. These providers must already be registered in the subscription:

`Microsoft.Network`, `Microsoft.ManagedIdentity`, `Microsoft.Storage`, `Microsoft.KeyVault`, `Microsoft.ContainerRegistry`, `Microsoft.Insights`, `Microsoft.MachineLearningServices`.

The Log Analytics workspace's subscription also needs `Microsoft.OperationalInsights`, and the portal needs `Microsoft.Web`.

## Quotas

| Quota | Requirement | How to check |
| --- | --- | --- |
| Azure ML `TotalLowPriorityCores` | 24 free cores | [Compute and cost](./architecture/compute-and-cost.mdx#quota-and-capacity) |
| Azure ML `standardNCADSA100v4Family` low priority | 24 free cores, or `-1` for a shared pool | Same |
| App Service plan SKU in the region | 1 VM of the SKU you choose, when `portal` is set | The usages API does not show the per-SKU limit. The definitive test is to create and delete an empty B1 Linux plan. |

Quota does not guarantee Spot capacity at run time. Check the A100 SKU is unrestricted in your region with `az vm list-skus`, as shown on the same page.

A zero-quota App Service SKU fails the foundation apply with `Current Limit (<sku> VMs): 0`. Nothing is deleted, and a rerun after the quota is granted continues from where it stopped.

## Permissions

| Who | Needs |
| --- | --- |
| Foundation plan and apply identity | The reviewed resource, scoped IAM, existing-subnet join and DNS-zone association permissions that `infra\` needs. Plan permission is not tenant administration. Role assignment writes are not part of Contributor, so confirm this with the subscription owner. |
| Publisher (`publisher_principal_id`) | Release-container writes, registry push and Azure ML environment and model registration. No compute, job or IAM writes. |
| Server deployment identity | Reads of the server catalog and release, registry pull, storage metadata reads, and the one site's read, configuration and start or stop. |
| Operator (`operator_principal_id`) | Receives scoped lifecycle and recovery access. This is an Entra object ID, and not a creator's browser identity. |
| Recovery identity | Reads workspaces and jobs, cancels jobs, reads and deletes the studio's own compute and egress, and reads and stops the shared site. It needs no compute creation, registry push or Terraform-state access. |
| Identity owner | Directory rights to create the registration, groups and app role assignments, and to grant admin consent. This is manual work. See `docs\operations\entra-bootstrap.md`. |
| Network owner | Can edit the supplied subnets, zones, links and NSG. |

Each workflow environment uses its own approved federated Azure identity. No workflow creates credentials or grants tenant consent. The permission contracts are in `docs\operations\private-pipelines.md` and `docs\operations\ownership-and-permissions.md`. None of them has been validated in a real tenant.

`operator_principal_id` is the Entra object ID, not the application or client ID. Look it up with `az ad signed-in-user show --query id --output tsv` while signed in as that user.

## Azure CLI context for the recovery script

The recovery script uses your Azure CLI session and accepts no alternate credentials.

```powershell
az login --tenant <tenant-id>
az account set --subscription <subscription-id>
```

If the signed-in tenant or subscription differs from the configuration, the script stops. In a workflow, `Azure/login` creates a short-lived federated CLI session in an isolated config directory, and the tools check tenant, subscription and cloud before any write. Child processes discard ambient `ARM_*`, `TF_VAR_*` and service-principal secrets.

If you keep one Azure CLI profile per customer, activate the right one before each run, in the same shell. A default resource group set in that profile can break `az acr` commands, so pass `--resource-group` explicitly.

Keep the settings document and the Terraform input outside the repository. The recovery script reads the settings document from the path you pass with `-SettingsPath`, and the workflows read it from protected environment secrets or approved runner paths. Restrict access to them and never copy them between deployments.

## Private network access

The foundation workflow talks to ARM and to the private state and artifact containers. Promotion and server deployment also reach private endpoints (blob, vault, registry, workspace, site), so the runner needs private DNS resolution and a network path to every region. The pipeline checks that the resolved service addresses are in private ranges and that TCP 443 answers, and fails early if not. Creators and administrators need the same resolution for the site.

## Package feeds in an enterprise environment

Several steps download packages, and an enterprise that blocks public registries has to point each ecosystem at one approved feed. The repository does not include your feed, and the workflows do not fall back to a public one. Check these places:

| Ecosystem | Where it is configured | What to do |
| --- | --- | --- |
| NuGet | Repo-root `nuget.config` | The file clears all sources and lists one. Replace the single source with your feed. The Docker build copies this file. |
| npm | `web\.npmrc` | Set `registry=` to your feed. |
| PyPI | The `PIP_INDEX_URL` values in the workflow files, and the feed URL for the GPU build | The workflow files ship a default Python index. Review it and replace it with your approved feed. Customer feeds need an explicit reviewed change. |

Feed credentials come from optional protected runner paths (`STUDIO_NPMRC`, `STUDIO_NUGET_CONFIG` and `STUDIO_NETRC`) that point at user-level files, never at credential values. GPU feed URLs and authentication use BuildKit secret mounts, so they do not land in an image layer. Newly published package versions are often quarantined for a few days by enterprise feeds, so if a just-released version does not resolve, pin an older one.

One more place names a feed. The Copilot CLI that powers the video helper is downloaded by the SDK during the server build, from the npm registry set in `CopilotNpmRegistryUrl` in `src\VideoSafetyStudio.Infrastructure\VideoSafetyStudio.Infrastructure.csproj`. Point that at your feed too. (`docs\app-service.md` describes this download as coming from GitHub releases. The csproj is the source of truth.)

:::note Historical
The guard used to be Python (`cost_guard.py`, patched into the upstream runner) and the arming gate was an `armed.json` file written by a PowerShell script. Both are deleted. The rules were ported to .NET. This page describes the .NET code. Nothing here has been verified against live Azure.
:::

The cost model is unchanged: one node, Spot, minimum zero, maximum one, and a server-side timeout on every job. The A100 default is `Standard_NC24ads_A100_v4`, idle scale-down is 120 seconds, the per-job maximum is 120 minutes (configurable per region within that), and there is no dedicated or larger fallback. Compute has no public IP or SSH.

## What armed means

"Armed" is a durable per-region phase, not a file. `StudioArmedGate` in `src\VideoSafetyStudio.Application\Operations\` reads a snapshot of the operations state:

- A region is armed only while a recent, validated snapshot says its phase is `Armed`. A missing, stale or fenced snapshot means no generation, so an unavailable control store or a host restart fails closed.
- `Fence()` drops the snapshot immediately. The next durable read restores only what the store still proves armed.
- Armed is eligibility, not a node. An armed region with zero nodes costs nothing for compute.
- The gate also tracks which release a region is armed with.

The hosted lifecycle that writes this state is described in [Hosted lifecycle](/deployment/guides/hosted-lifecycle). The UI shows the result as `armed` and `generationEnabled` in the status response; see [Web UI overview](../web-ui/overview.mdx).

## What the guard checks per job

`AzureMlGuard.Validate` runs in `src\VideoSafetyStudio.Infrastructure\AzureMl\AzureMlGuard.cs` before a job is created. `RegionalAzureMlBackend` calls it with `gate.IsArmed(region)` on every attempt, so a Stop between attempts blocks the next one. It throws `AzureMlSafetyException` on the first failure. In the order the code checks them:

1. The region is armed.
2. The experiment, compute name and compute id match the region's foundation.
3. The timeout is 1 to 7200 seconds (`MaxSeconds` in `AzureMlJobSpec.cs`).
4. The instance count is exactly one.
5. The batch size is exactly one video.
6. The command, environment id, models reference, code URI and models kind equal what the selected release defines. A job cannot point at an unprepared environment.
7. The compute identity client id matches the foundation's.
8. The output is a private datastore path under `video-library/`.
9. The input image and workflow are private datastore paths under `studio/web-inputs/`, not signed URLs.

A datastore path is accepted by `IsDatastorePath` only if it has the exact prefix and content after it, and contains no `?`, `#`, `..`, backslash or `%`.

### Read-back after submit

A guard that only checks the request trusts the request. `AzureMlGuard.VerifyCreated` checks the job Azure ML stored:

- The returned job name equals the submitted name.
- The server timeout exists and does not exceed the smaller of the maximum and the requested timeout. `NormalizeTimeout` accepts a number, a numeric string or an ISO 8601 duration, and refuses anything else rather than assuming a limit.
- The instance count is present and exactly one.
- The job is assigned to the region's studio compute.

In `RegionalAzureMlBackend`, a failed read-back cancels the job. The create call is never retried, and an uncertain create result is checked with a GET. The server-side behavior of cancel against real Azure is not verified.

## What the lifecycle checks before Start

`StudioLifecycle` and `StudioPolicy` (in `Operations\`) hold the live-resource contracts that the operator script used to hold. Start refuses unless spend is approved (`Start requires explicit approval of variable Spot GPU spend (one node per job)`) and the live checks pass:

- The workspace, dedicated GPU subnet, NSG and any existing NAT match the expected ids and ownership tags. A resource the studio does not own is refused, not adopted.
- The compute that exists (or is created) matches the contract: `AmlCompute`, the configured VM size, `LowPriority`, minimum 0, the regional maximum, idle `PT120S`, no public node IP, remote login disabled, one user-assigned identity.
- Owned NAT and public IP linkage is ready before submissions open.
- No queued or running job on that compute could resume. A job with an unreadable compute or status blocks.
- One exact Linux pay-as-you-go rate for the SKU is at or below the regional threshold. This is a price ceiling. The code logs that it is not a Spot bid, billing cap or capacity guarantee.
- The A100 SKU is unrestricted, and Spot and A100 family quota cover 24 cores.

Settings changes are bounded by the deployed policy. A per-region job timeout above the deployed limit, or above 120 minutes, is refused.

## What Stop guarantees

Stop closes the fence first, so submissions are off before slow cloud work starts. It then cancels jobs, deletes only the studio's own compute with its underlying resources, waits for absence, proves every relevant job is terminal, and removes only the studio's own NAT and public IP. It reports every failure and is safe to repeat. See [Hosted lifecycle](/deployment/guides/hosted-lifecycle).

`scripts\recovery\Stop-Studio.ps1` releases compute independently of the host. Stop is not a zero bill: registry, storage, models, videos, private endpoints and logging remain.

:::warning
When you change anything in this path, run the [tests](./testing.mdx) first. The guard tests are written to fail closed: an unrecognized input must be rejected.
:::

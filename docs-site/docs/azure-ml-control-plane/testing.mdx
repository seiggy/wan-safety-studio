None of these checks touch Azure. They use stand-in SDK modules, fixture receipts and fake resources, so they cost nothing and need no login. Run them on every change to the safety code.

## The three suites

| Suite | Run with | Needs |
|---|---|---|
| `azureml\test_controls.py` | `python azureml\test_controls.py --scratch <dir>` | Python 3.11 or 3.12, standard library only |
| `azureml\Test-Controls.ps1` | `pwsh azureml\Test-Controls.ps1` (or `scripts\Invoke-WanSafetyStudio.ps1 -Action Check`) | PowerShell 7.4+; also runs the Python suite |
| `azureml\test_sdk_controls.py` | `python azureml\test_sdk_controls.py --upstream <checkout> --scratch <dir>` | The installed Azure ML SDK and a checkout of the exact pinned upstream commit |

Run the first one while you work. It takes about five seconds on a normal machine:

```powershell
python azureml\test_controls.py --scratch $env:TEMP\tc
...
Ran 34 tests in 5.104s

OK (skipped=1)
```

The skipped test is the one that applies the real upstream patch. It needs `WAN_STUDIO_UPSTREAM_TEST_ROOT` pointing at a checkout of the pinned commit and skips itself with that message otherwise. Set it before you touch `upstream-cost.patch`.

Use a scratch directory outside the repo. The suites create and delete files there.

`test_controls.py` is "framework-free": `unittest` and `unittest.mock` only. Heavy modules (`azure.ai.ml`, `azure.identity`, OpenTelemetry) are replaced with small `module(...)` and `Entity` stand-ins at the top of the file, so you do not need the locked environment to run it.

### Writing a test

Tests here describe a rejected input. The existing ones for the timeout show the shape: build valid arguments, break exactly one thing, and assert that the guard raises.

```python title="azureml/test_controls.py"
args.timeout_seconds = 7201
with self.assertRaises(ValueError):
    if function_name == "build_job":
        namespace[function_name](args, work, environment_ref=args.environment_id,
            models_ref=args.models_path, profile=profile)
    else:
        namespace[function_name](args)
```

A new rule needs two tests: one that proves the valid case passes (so the rule is not just rejecting everything) and one for each way it should fail. If you add a field to the foundation receipt, add it to the fixtures in `infra\tests\fixtures\studio-*.json` as well, because both the Python and PowerShell suites read them.

## What the PowerShell suite covers

`Test-Controls.ps1` dot-sources `Invoke-WanSafetyStudio.ps1 -Action Status`, which loads the functions without running a lifecycle action, then calls them against fixture receipts for three modes (`off`, `on`, `customer-nsg`). A `Must-Reject` helper asserts that an unsafe call throws:

```powershell title="azureml/Test-Controls.ps1"
function Must-Reject([scriptblock]$Test) {
    $rejected = $false
    try { & $Test | Out-Null } catch { $rejected = $true }
    if (-not $rejected) { throw 'A fail-closed test unexpectedly accepted unsafe input.' }
}
```

It checks the Azure context and subscription binding, configuration parsing, `Set-Foundation` against good and bad receipts, the child-process environment (no secrets, no alternate package index, no unsafe TLS flags), exact-owner checks, compute egress, subnet shape, cluster shape, the PAYG rate selection and quota rules, `Start`, `Stop` and `Deploy` flows with the ARM and Terraform calls replaced by functions that record what they were asked to do.

Pass `-PowerShellOnly` to skip the Python suite at the end. On success it prints `PASS: framework-free portable scope, process, price/quota, Start and exact-owned Stop checks. No Azure mutations or GPU allocations.`

The script creates its working files under `azureml\.check\` and removes them in a `finally` block.

## SDK integration check

`test_sdk_controls.py` is the one that uses real SDK classes. It asserts that the upstream checkout's HEAD equals `UPSTREAM_SHA`, applies the patch to a clean export of it, stages the code snapshot with `runtime.snapshot`, and then runs the real job builders for the `wan` and `minimax_h3` profiles with a mocked Azure ML client. For each it checks the managed identity, the private-datastore inputs and output, an empty environment, a single `create_or_update`, the read-back `get`, and that a job whose server limits are missing is canceled once and never resubmitted. It is the check that the patch still applies when you bump the SDK or the upstream commit. Run it with the locked environment from the cache (`<cache>\venv`).

## When you bump a pin

If you change `UPSTREAM_SHA`, a model revision, the base image digest or `uv.lock`:

1. Run `test_controls.py` with `WAN_STUDIO_UPSTREAM_TEST_ROOT` set to the new upstream checkout.
2. Run `test_sdk_controls.py` against the same checkout.
3. Run `Test-Controls.ps1`.
4. Expect Prepare to run again on every machine, because each of those files is part of the [release version](./overview.mdx#release-version).

These suites run offline on purpose. They say nothing about whether a real Spot node is available or the workflow produces a good video, so the first real `Submit` after a pin change is still your smoke test.

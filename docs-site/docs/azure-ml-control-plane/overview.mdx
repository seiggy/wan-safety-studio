:::note Historical: the Python control plane is gone
Earlier versions of this page described a Python operator control plane in `azureml\` that a PowerShell script drove (Prepare, Start, Stop, an operator cache, a release hash). That folder, the Python operator control plane, and the Initialize, hook and upload scripts that supported it were deleted in the P9 cleanup. The sections below describe what replaced them. Nothing in this section has been verified against live Azure.
:::

## The three execution boundaries

The studio now runs in three places. Each owns a different part of what the operator script and `azureml\` used to do.

| Boundary | Owns |
|---|---|
| .NET App Service | Operations (Start, Stop, Status), generation routing across regions, the admin UI, and the submission guard |
| GitHub Actions | Building the GPU image and model snapshot, promoting a release into each region, deploying the server and foundation |
| Python/ComfyUI containers run by Azure ML jobs | Running the upstream ComfyUI runner on the GPU node, and nothing else |

The job on the node executes only the upstream ComfyUI runner. No Python cost guard runs inside the job. The guard runs in the .NET server before and after submission.

## Where each former responsibility lives

| Former responsibility | Now | Page |
|---|---|---|
| Cost and submission guard (Python `cost_guard.py`, patched into the upstream runner) | .NET port in `AzureMlGuard.cs`, `AzureMlJobSpec.cs` and `RegionalAzureMlBackend.cs`, plus the lifecycle checks in `StudioLifecycle` and `StudioPolicy` | [Cost guard and safety](./cost-guard-and-safety.mdx) |
| Prepare: build the image, stage models, register and publish a release | `build\gpu` (see its `README.md`), driven by the `release.yml` workflow and `scripts\ci\*.py`. Promotion per region is `promote.yml` (`scripts\ci\publish_region.py`) | [Private pipelines](/deployment/guides/private-pipelines) |
| Start, Stop, Status | The hosted lifecycle in the .NET server. An independent emergency release script is `scripts\recovery\Stop-Studio.ps1` | [Hosted lifecycle](/deployment/guides/hosted-lifecycle) |
| Armed gate (`armed.json` in an operator cache) | A durable per-region state in the control store, read by `StudioArmedGate` | [Cost guard and safety](./cost-guard-and-safety.mdx#what-armed-means) |
| Checks (`Test-Controls.ps1`, the Python suites) | .NET tests, `build\gpu`, `infra` and `scripts\ci` tests, and the recovery mocks | [Testing](./testing.mdx) |

Regional routing, admission and recovery are described in `docs\operations\hosted-lifecycle.md`. The pipeline boundary is in `docs\operations\private-pipelines.md`.

## What stayed true

These cost controls are unchanged. The .NET code enforces them in `StudioPolicy`, `StudioContractRules` and `AzureMlGuard`:

- The default VM size is `Standard_NC24ads_A100_v4`, as Spot (`LowPriority`).
- Minimum nodes 0, maximum 1 by default. Each job uses exactly one instance.
- Idle scale-down is 120 seconds.
- A job's maximum runtime is 120 minutes. Each region can configure a lower limit, never a higher one.
- There is no dedicated or larger-SKU fallback.
- Nodes have no public IP and remote login is disabled.

## The frozen legacy script

`scripts\Invoke-WanSafetyStudio.ps1` still exists, but it is frozen. It accepts only `-Action Status`, `Stop` and `Check`, and exists for the emergency release of a deployment made before the migration (v1). `scripts\Test-LegacyLifecycle.ps1` is its offline test. Both will be deleted once the v1 to v2 migration is verified. Do not extend them. For a current deployment, use the hosted lifecycle and `scripts\recovery\Stop-Studio.ps1`.

## Not verified

The hosted lifecycle, the regional backend and the pipelines are tested offline with mocks. Their behavior against real Azure (permissions, private routing, how Azure ML reports a queued Spot job, whether Spot capacity is granted) has not been verified live.

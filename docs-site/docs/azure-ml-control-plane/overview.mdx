Generation on Azure runs as Azure ML command jobs on one Spot A100 node (minimum 0, maximum 1). Nothing in the studio server creates that compute. An operator does, with the script `scripts\Invoke-WanSafetyStudio.ps1` and the Python code in `azureml\`. The .NET server only submits jobs to compute that is already armed; see [Azure ML provider](../domains/azure-ml-provider.mdx).

This page covers the operator side. The rules that protect the bill are on [Cost guard and safety](./cost-guard-and-safety.mdx), and the checks that prove them are on [Testing](./testing.mdx).

## Who does what

`AGENTS.md` describes `azureml\` as the Python control plane with Prepare, Start, Stop, Submit and Status. In the code the work is divided differently, and it matters when you look for a bug.

| Action | Where it runs | What it does |
|---|---|---|
| `Deploy` | PowerShell + Terraform | Applies the foundation. Needs `-ApprovePersistentCosts`. Never arms submission |
| `Prepare` | PowerShell, then `azureml\runtime.py prepare` | Builds and verifies every asset on CPU, writes `prepared-<profile>.json` |
| `Start` | PowerShell + ARM REST | Checks price and quota, creates compute, writes `armed.json`, starts the local server |
| `Submit` | PowerShell, then `azureml\runtime.py submit` | One smoke job with a supplied image, optionally waits and verifies the MP4 |
| `Stop` | PowerShell + ARM REST only | Disarms, cancels jobs, deletes compute, NAT and public IP, reconciles Terraform |
| `Status` | PowerShell + ARM REST | Reports `OFF`, `IDLE`, `RUNNING/NODESALLOCATED` or `PARTIAL/ERROR` |
| `Check` | PowerShell | Runs `azureml\Test-Controls.ps1` |

Python's command line has exactly three actions, defined in `runtime.py`:

```python title="azureml/runtime.py"
commands = parser.add_subparsers(dest="action", required=True)
for name in ("prepare", "verify", "submit"):
    sub = commands.add_parser(name)
    sub.add_argument("--profile", choices=("wan",) if name == "submit" else ("wan", "ltx", "ltx_i2v", "minimax_h3"), required=True)
```

`Start`, `Stop` and `Status` are not in Python on purpose. The script's comment on Stop says "Emergency release deliberately has no Prepare, Python, Docker, retail or preview prerequisite." A broken Python environment must not stop you turning the GPU off, so release uses only `az`, ARM REST and Terraform.

### Why Prepare is Python

Prepare builds on code that is already Python. The job runtime is an upstream project (`jakeatmsft/azureml_vidgen_comfyui`, pinned to one commit) that uses the Azure ML SDK, and the studio patches it (`upstream-cost.patch`) so its job factories call the studio's cost guard. Prepare has to import that upstream package, build its Docker image, snapshot its code and call the SDK to register an environment and a model. Doing that in PowerShell would mean reimplementing the SDK calls. The package set is locked in `pyproject.toml` and `uv.lock` (`azure-ai-ml==1.30.0`, `azure-identity`, `msal`, `azure-storage-blob`, `aiohttp`, `Pillow`, OpenTelemetry).

## The operator cache

State lives in one directory per deployment, outside the repo. Set it with `WAN_STUDIO_CACHE`, or let the script choose `%LOCALAPPDATA%\wan-safety-studio\<subscription-id>-<deployment-name>` on Windows (`~/.cache/...` or `~/Library/Caches/...` elsewhere).

| Entry | Purpose |
|---|---|
| `foundation.json` | Terraform outputs for the selected deployment (workspace, compute, storage, registry) |
| `prepared-<profile>.json` | The prepared release: version, image digest, model and code records, scope fingerprint |
| `armed.json` | Written by Start, removed by Stop. Its presence is "submission is armed" |
| `release-required.json` | Written at the start of Stop, removed only when release is verified |
| `portal.json` | State of the locally started server process |
| `venv\`, `python-project\` | The locked Python environment and the reviewed lock it was built from |
| `source-<version>\`, `source-<version>.json` | The patched upstream checkout and its diff hash |
| `assets-<version>-<profile>\`, `image-<version>-<profile>\` | Staged code, models and Docker context |
| `models\wan\` | Optional local copy of the weights to reuse |
| `scratch\` | Temp directory, so upstream helpers never write elsewhere |
| `last-job.json` | The most recent smoke job |

`write_json` writes to a `.pending` file and renames it, so a crash never leaves half a JSON document.

Deleting the cache leaves Azure resources alone and throws away the prepared release and the armed gate. Run Prepare again before Start.

## Release version

`version_key` in `runtime.py` is the release identity. It hashes the files that define behavior and the deployment:

```python title="azureml/runtime.py"
def version_key(cache: Path):
    digest = hashlib.sha256()
    for name in ("upstream-cost.patch", "config.py", "cost_guard.py", "runtime.py", "models.py",
                 "wan-pinned-manifest.json", "pyproject.toml", "uv.lock"):
        digest.update((HERE / name).read_bytes())
    digest.update(deployment_fingerprint().encode())
    digest.update(package_index_url().encode())
    if (cache / "python-project" / "uv.lock").read_bytes() != (HERE / "uv.lock").read_bytes():
        raise ValueError("Cached dependency lock differs from the reviewed project lock; rerun Prepare.")
    return f"{UPSTREAM_SHA[:12]}-{digest.hexdigest()[:16]}"
```

So the version reads like `dc0d29031b73-<16 hex>`. Edit any of those eight files and the version changes, which invalidates `prepared-<profile>.json` and forces Prepare to run again before Start. This is intended. A change to `cost_guard.py` should never run against assets prepared under the old one.

`deployment_fingerprint` hashes the Terraform config and the foundation receipt, minus `compute_enabled` and `portal`. Those two can change between Start and Stop, or when the web host is added later, without touching any prepared asset. A second hash, `scope_fingerprint`, covers the subscription, tenant, resource group, workspace, compute, identity, storage and datastore. It is stored in the prepared file and rechecked on every use.

## The pinned manifest

`wan-pinned-manifest.json` lists every model file the WAN workflow downloads: the 14B high and low noise diffusion models, the text encoder, two VAEs, two 4-step LoRAs and the 5B TI2V checkpoint. Each entry has a folder, file name, URL, byte size and SHA-256.

```json title="azureml/wan-pinned-manifest.json"
{
  "folder_name": "vae",
  "filename": "wan_2.1_vae.safetensors",
  "url": "https://huggingface.co/Comfy-Org/Wan_2.2_ComfyUI_Repackaged/resolve/c4f60d30c55a624e35427060fdd217579a6c1d77/split_files/vae/wan_2.1_vae.safetensors",
  "size": 253815318,
  "sha256": "2fc39d31359a4b0a64f55876d8ff7fa8d780956ae2cb13463b0223e15148976b"
}
```

`load_wan_manifest` in `models.py` rejects the file unless all of these hold:

- Keys are unique and the four base models are present (`REQUIRED_WAN_MODELS`).
- The URL is a Hugging Face `resolve/<40-hex commit>/...` link. A branch name such as `main` fails.
- The repository and commit match `WAN_REVISIONS`, and the path has the expected shape (`split_files/<folder>/<file>`, or `TI2V/<file>` for the one Kijai repository).
- Size is a positive integer and the SHA-256 is 64 hex characters.

Adding a model means adding an entry and, if it comes from a new repository, adding that repository and commit to `WAN_REVISIONS`. Because `wan-pinned-manifest.json` is in the version hash, the change forces a new Prepare. The tests in `test_controls.py` (`test_wan_manifest_integrity`, `test_wan_revision_pins`) fail if the manifest and the code disagree.

Other profiles (`ltx`, `ltx_i2v`, `minimax_h3`) exist in Prepare. But the portal and the smoke Submit support WAN only, so treat them as experimental.

## Credentials and telemetry

The Python code authenticates with `AzureCliCredential` pinned to the configured tenant, after `assert_cli_scope` confirms `az account show` matches the selected subscription and tenant. There are no keys in the control plane. Traces and logs go through OpenTelemetry (`telemetry.py`) to whatever OTLP endpoint Aspire or a collector provides, and spans are created with `record_exception=False` so a failure cannot write a signed URL into a trace.

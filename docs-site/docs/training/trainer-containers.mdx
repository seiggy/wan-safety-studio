A trainer is a Docker image. The server never imports it. It reads a `trainer.json`, runs the image with a dataset mounted read-only and an output folder mounted writable, and collects what the image wrote. How the server drives a run is on the [YOLOX pipeline](./yolox-pipeline.mdx) page. This page is about the image itself.

## The container interface

The server runs exactly this:

```text
docker run --rm --gpus all --shm-size 8g -v <data>:/data:ro -v <out>:/out <image> all --preset <p> [--epochs N]
```

| Mount | Contents |
|---|---|
| `/data` (read-only) | `classes.json` (a list of names), `train.json` and `val.json` (COCO; `file_name` is relative to `/data`, category ids are 1-based), and `images\` |
| `/out` (writable) | Everything the trainer produces. The server copies all of it to the run's `out\` folder |

After a successful `all`, the server looks for `metrics.json` in `/out` and shows its numbers. Other files it expects by convention, from `sdk.py`: `model.onnx`, `model.json`, and a `deepstream\` folder with the `nvinfer` config, `labels.txt` and `NOTES.txt`.

The default `--data` and `--out` arguments in `run_cli` are `/data` and `/out`, so the image needs no arguments beyond the ones above.

## The SDK

`trainers\sdk.py` is one file with no dependencies beyond the standard library, so an image can copy it as is. It defines the data types and the `Trainer` protocol:

```python title="trainers/sdk.py"
class Trainer(Protocol):
    info: TrainerInfo

    def train(self, request: TrainRequest) -> Path:
        """Train or resume; return the best weights file under request.out."""

    def evaluate(self, weights: Path, request: TrainRequest) -> Metrics:
        """Score the weights on val.json."""

    def export(self, weights: Path, out: Path) -> OnnxModel:
        """Write model.onnx (and anything it needs) under out."""

    def deepstream(self, model: OnnxModel, classes: tuple[str, ...]) -> DeepStreamConfig:
        """nvinfer config, labels and any parser notes for DeepStream on Jetson."""
```

| Type | Fields |
|---|---|
| `TrainerInfo` | `name`, `version`, `license_code`, `license_weights`, `presets`, `default_preset` |
| `TrainRequest` | `data`, `out`, `preset`, `classes`, optional `epochs`, optional `resume` |
| `Metrics` | `map50`, `map50_95`, `per_class` |
| `OnnxModel` | `path`, `input_size` as (width, height), `input_name`, `output_names` |
| `DeepStreamConfig` | `files` (name to text) and `notes` |

`run_cli(trainer, argv)` is the entry point. It accepts a command (`info`, `train`, `evaluate`, `export`, `deepstream`, `all`), `--data`, `--out`, `--preset`, `--epochs` and `--resume`. It rejects a preset that is not in `info.presets`, reads `classes.json`, and runs the steps the command names. `all` is `train`, `evaluate`, `export`, `deepstream` in that order and writes:

| File | Written by |
|---|---|
| `metrics.json` | `evaluate` |
| `model.json` | `export` (the `OnnxModel` as JSON) |
| `deepstream\<name>` and `deepstream\NOTES.txt` | `deepstream` |

Weights and `model.onnx` are written by your own `train` and `export` methods. `run_cli` makes no assumption about their names except that `evaluate` is handed whatever `train` returned.

The `info` command prints the manifest data as JSON and needs no dataset, which makes it a cheap smoke test that the image starts:

```powershell
docker run --rm wan-trainer-yolox:dev info
```

## The registry: trainer.json

`FileTrainerRegistry` on the server scans for `trainer.json` files and builds the trainer list the UI shows. A folder whose name starts with `_` is skipped, which is how `_template` stays out of the list. A manifest is accepted only if it has a name, at least one preset, and a `defaultPreset` that is one of them.

```json title="trainers/yolox/trainer.json"
{
  "name": "yolox",
  "version": "0.1.0",
  "image": "wan-trainer-yolox:dev",
  "licenseCode": "Apache-2.0",
  "licenseWeights": "Apache-2.0 (YOLOX release weights, initialised from COCO; COCO annotations CC BY 4.0, attribution required)",
  "presets": ["nano", "tiny", "s"],
  "defaultPreset": "nano"
}
```

The Train panel shows both licences under the trainer select, so a user sees the weights licence before starting.

Where the server looks is set by the `Trainers` configuration section (`TrainerOptions`): `BuiltIn` is `../../trainers` in `appsettings.json`, and `Directories` is a list of extra roots. Each root is searched recursively. If two trainers share a name, the one found later wins, and the built-in folder is read last.

To add a customer folder, bind the list in the usual .NET way, for example `Trainers__Directories__0=D:\customer-trainers` in the server's environment.

:::note
`docs\vision-trainers.md` and the `_template` README mention an environment variable `WAN_STUDIO_TRAINERS_DIR` for this. The server's configuration guide says the server reads none of the `WAN_STUDIO_*` variables, and I found no code reading it. Use the `Trainers` section until that is reconciled.
:::

## Build the YOLOX image

```powershell
docker build -f trainers/yolox/Dockerfile -t wan-trainer-yolox:dev trainers
```

The build context is `trainers\`, because the Dockerfile copies `sdk.py` and the `yolox` folder from it. On a feed-only machine pass the package index with `--build-arg PIP_INDEX_URL=<feed>`.

What the Dockerfile does:

- Starts from `pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime` (build arg `BASE`).
- Clones YOLOX and checks out the pinned commit `6ddff4824372906469a7fae2dc3206c7aa4bbaee` (`YOLOX_COMMIT`), then installs its requirements and the repo with `pip install --no-deps -e .`.
- Downloads `yolox_nano.pth`, `yolox_tiny.pth` and `yolox_s.pth` from the YOLOX `0.1.1rc0` release into `/weights` and writes `/weights/SHA256SUMS`. Put those hashes in the model card.
- Copies the SDK and trainer into `vision/trainers/` and sets `ENTRYPOINT ["python", "-m", "vision.trainers.yolox"]`.

The trainer code keeps the module path `vision.trainers.*` that it was written with, which is why the Dockerfile creates that package skeleton. A new trainer must use the same path in its imports, or change both the Dockerfile and the imports together.

But the image has not been run on a GPU yet. See [what nobody has verified](./yolox-pipeline.mdx#what-nobody-has-verified).

The template's README also says to run `python -m unittest test_trainer_contract` after adding your class to `CONTRACT_TRAINERS`. I could not find a `test_trainer_contract` file in the repo, so there is no contract test to run today. Writing one would be a good first contribution; it should instantiate each trainer, check `info` (default preset in presets) and run `run_cli` with `info`.

## Rules for trainers

- **Licences are part of the manifest.** The plan excludes AGPL detectors. Record the code licence and the weights licence separately, because they often differ.
- **Fail loudly.** A non-zero exit becomes a `Failed` run with a truncated message, and `train.log` is kept either way. Raise instead of returning partial results.
- **No network at run time.** Bake weights into the image. A trainer that downloads during a run cannot work in a private network.
- **One run at a time.** The server holds a single-slot lock, so do not design around parallel runs.
- **Keep dataset-specific logic inside the trainer.** The shared layout (`classes.json`, two COCO files, `images\`) is the whole contract.
